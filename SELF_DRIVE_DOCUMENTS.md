# Self Drive document verification — testing only

## Setup required before using the testing preview

1. Apply `supabase/migrations/20260919_self_drive_documents.sql` in the Supabase project used by the testing preview. This creates only the two Self Drive tables, a private `self-drive-documents` bucket, and a restrictive policy scoped to that bucket. It does not modify partner storage or existing table policies.
2. Add `SELF_DRIVE_TOKEN_SECRET` to Vercel **Preview**, scoped to `testing`: use a cryptographically random secret of at least 32 characters. Do not put the value in the repository or frontend. Existing `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `RESEND_API_KEY` are reused server-side. Redeploy `testing` only after setup.
3. Do not enable public access or client policies for either new table or the new bucket. The server uses the existing service-role key. Browser uploads use a signed, single-document upload URL and do not receive a service-role key or any read/download URL.

No Supabase management connection is available in this workspace. The migration is supplied but has not been applied remotely. Actual Supabase bucket/RLS behavior and live Resend delivery must be verified on the configured testing preview; automated tests use mocks.

## Flow and security

- Existing Self Drive booking generation and validation are retained. The booking endpoint creates a `self_drive_verifications` row before sending the existing admin/customer notifications. With Driver bypasses this flow completely.
- The browser creates a 256-bit random submission nonce. The server derives an HMAC token using the server-only secret, stores its SHA-256 hash plus a server-encrypted copy for authorized re-upload emails, and returns a booking-specific upload link. Retrying the same submission preserves its token; other requests cannot retrieve it with a Booking ID. Booking reference collisions return an error instead of replacing the existing request.
- Links expire after seven days. The secret link's token is in the URL fragment (not query parameters), with no-referrer/noindex and no third-party scripts on the upload page. Do not share these bearer links. Tokens are used only in the API Authorization header; never log or email document URLs.
- Required files: Aadhaar, Driving Licence front, Driving Licence back, PAN, current address proof. Alternate mobile number is required on final submit.
- Selecting files only creates local previews. Small images (up to 1 MB) and PDFs are unchanged. Larger images are reduced to at most 2400 pixels on the longest edge at JPEG quality 0.9 only if this saves space; the user should inspect readability before submitting. Final file limit is 5 MiB (5 MB displayed). Very large source images over 30 MiB are rejected to bound browser memory use.
- Uploads start only on Submit Documents, one file at a time. Storage paths are `self-drive-documents/<BOOKING_ID>/<document-kind>`. Signed upload URLs allow no overwrite and expire after Supabase's two-hour window. Expired booking tokens cannot request more URLs or finalize. A URL issued before expiry may finish its bounded upload; it grants no read access.
- Both the browser and server check allowed types and size. The server reads the private uploaded object and checks MIME type, size and file signature before registering it. Invalid objects are deleted. This is format validation, not identity verification or malware scanning.
- Verified file receipts are stored in `self_drive_document_files`. A retry checks for an existing receipt/object before issuing a new upload URL, including when a successful upload response was lost. Successful files are not uploaded again. Refresh restores uploaded-file status; unuploaded local files must be selected again.
- Final submission requires all five validated receipts and alternate mobile number. It writes only `pending_verification` and `submitted_at`; it never confirms a booking. Approved documents cannot be replaced through the upload link. Rejected documents receive a new versioned upload path; their previous objects are never overwritten.
- Manual review uses authorized Supabase access to the private bucket and the corresponding booking row. The authenticated `/self-drive-review` page now supports manual review; there is no automatic approval. Apply your document-retention process using authorized server/dashboard access.

## Admin review and selective re-upload extension

Apply `supabase/migrations/20260919_self_drive_review.sql` **after** the original migration, in the testing Supabase project. The new migration is provided only; it has not been applied remotely. It extends existing rows in place with per-document status/reason, reviewer/time, upload revision, verification metadata, and notification event/receipt fields. The bucket remains private; existing RLS restrictions remain unchanged. Only the service role can invoke the three transaction functions. These functions lock the booking row, reject stale revisions, keep approved files immutable, and require all five approvals before verification.

The existing Supabase admin login/session is reused. By default, only the confirmed Supabase user with email `carwithdriver.vikhroli@gmail.com` may review documents. If your existing admin account differs, set optional server-only `SELF_DRIVE_ADMIN_EMAILS` in the testing Vercel Preview environment to a comma-separated reviewer allowlist. No new mandatory secret or separate login system is needed. Keep the existing `SELF_DRIVE_TOKEN_SECRET` stable: it also encrypts stored upload tokens with AES-GCM. Old rows containing only a token hash can still be read/reviewed; before requesting re-upload on such a row, the customer must open their existing valid link once to securely backfill its encrypted copy. No plaintext token is returned to the admin browser.

After documents are submitted, the admin receives a Review Documents email linking to `/self-drive-review?booking=<BOOKING_ID>`. This URL grants no access without an authorized admin session. Sign in via the existing Admin Panel link, then Check Sign-in. Previews are generated on demand and expire after 60 seconds. They grant private read access only for that document; they are never included in emails.

Use Approve or enter a reason and select Request Re-upload on each document, then Save Review & Notify to apply the batch. Required reasons are included in one customer email for that batch. The same customer token is reused and renewed for seven days. Only rejected cards are editable; approved and other pending cards stay locked. Replacements use `<BOOKING_ID>/<kind>/v<revision>`, retain the prior private object, and return to Pending after validation. Submit Documents then moves the overall request to Pending Review and notifies admin again. Verify Documents is enabled only after every document is approved; verification sends an acknowledgement explicitly stating that the booking is not confirmed.

Notifications use the existing Resend sender/helper. Each transition has a persisted event ID and send receipt; repeat submissions and successful email retries do not resend. Failed email delivery never undoes a saved review or upload. Admin may use Retry Notification Email for the pending event. Resend idempotency also protects concurrent retries; as with the existing flow, an accepted send followed by an unavailable database beyond Resend's retention window cannot provide an absolute exactly-once guarantee. No background scheduler is added.

Run `node scripts/test-self-drive-review-browser.mjs` for the authenticated admin UI and single/multiple rejected-card flows. The PostgreSQL suite executes both migrations locally and covers transactional approval/rejection, unauthorized users, expiry/isolation, stale updates, approved locks and email retries. Existing notification, upload/compression and With Driver/Partner regressions remain available. Live Supabase Auth, Storage and Resend delivery still need verification on the configured testing preview. No remote migration was executed.
